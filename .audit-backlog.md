## Открыто
- [ ] **Дефекты навигации, найденные попутно** при разборе пустого экрана (не обещаны, не сделаны;
      к самому пустому экрану отношения не имеют — его причина найдена и закрыта):
      - `AppNavGraph` при `UiState.Connecting` не исключает маршрут `workspace/sessions/{id}`, так что
        любой транзитный реконнект **выдёргивает пользователя из открытого чата** на голый спиннер
        `connecting` (у него нет ни UI, ни таймаута).
      - Восстановление сохранённого маршрута вызывает **suspend** `loadSavedRoute()` внутри
        `LaunchedEffect(uiState)`: смена `uiState` во время этого IO отменяет эффект, и `navigate`
        не происходит — пользователь остаётся на `connecting`.
      - `onForget` делает `popUpTo(target)` для маршрута, которого в стеке обычно нет, — это no-op,
        под свежезабытым сервером остаются его же `settings` / `workspace`.
      - Тестов на навигацию в проекте нет ни одного, и `BackHandler` не используется нигде.

      удалены, compose-правила вернулись к простому `@get:Rule`. `:app` — те же 400 тестов,
      зелёные; golden-PNG не поменялись.
- [x] **Межпроцессный повтор после перезапуска редактора** (2026-09-08). `QueuedMessage` получил
      необязательное поле `attempt` (`QueuedSendAttempt`: `at_ms` + `instance_id`), которое
      `QueueController.dispatchOne` пишет **до** кадра. Отсутствие поля = «в транспорт не отдавали»,
      значит повтор после рестарта — первая доставка, и офлайн-очередь работает как раньше. Записи,
      поднятые с диска и уже имеющие `attempt`, проходят через предикат `:app`
      `canReplayRehydratedSend` — тонкую обёртку над существующим `canRequeueAmbiguousSend`, чтобы
      два пути повтора не разъезжались; отказ = `ReplayNotSafeException` и возврат текста в
      черновик. Вердикт по фичам берётся **один раз на flush** через ограниченное ожидание
      (`REPLAY_GATE_TIMEOUT_MS`, те же 30 с, что и `REPLAY_RENEGOTIATE_TIMEOUT_MS`), потому что
      `onConnected` выгружает очередь раньше, чем отвечает проба `capabilities`. Записи, поставленные
      в очередь **этим** процессом, не гейтятся: их неоднозначностью владеет живой вызывающий
      (`dispatchSendWithRetry`).
- [x] **`PersistedPendingSend.serverInstanceId` удалён** (2026-09-08). Маркер знал инстанс на момент
      **тапа**, а он отличается всякий раз, когда сообщение пережидает реконнект в очереди; у записей
      старых сборок его нет вовсе. Провенанс переехал на `QueuedMessage.attempt` — единственное
      место, где известно, в какой процесс кадр реально ушёл. Маркеры с ключом на диске
      декодируются по-прежнему: у `Json` репозитория стоит `ignoreUnknownKeys = true`.
- [x] **Шторм переподключений: два `RemoteClient` в одном процессе** (2026-09-08).
      **РЕГРЕССИЯ, НАЙДЕННАЯ В ПРОДЕ ПОСЛЕ ВЫКАТКИ АУДИТА, а не находка аудита.** Полный разбор:
      [`docs/findings/2026-09-08-duplicate-connection-storm.md`](docs/findings/2026-09-08-duplicate-connection-storm.md).
      Симптом: 576 аутентификаций за 3.5 часа в логе сервера, сообщения висят в «Waiting for
      connection», загрузка картинок падает на клиенте при `upload_finish OK` на сервере. Причина:
      `ConnectionManager` создаётся на `MainViewModel` (`MainViewModel.kt:172`, `scope = viewModelScope`),
      `MainViewModel` — на экземпляре `MainActivity` (`by viewModels()`), а `.MainActivity` была
      объявлена **без `launchMode`**, то есть `standard`, и второй экземпляр Activity в задаче
      создаётся штатно. Два экземпляра ⇒ два `MainViewModel` ⇒ два `ConnectionManager` ⇒ два клиента
      против одного десктопа; сервер держит одно соединение на клиентский id и вышибает старое с
      `1001 "evicted by new connection"`, каждый клиент читает это как обрыв сети и перезванивает.
      Диагноз закрыт двумя фактами из инструментированного лога: закрытие приходит **от сервера** с
      этим текстом, а счётчики `attempt` идут двумя независимыми сериями (`1,2,3,4,5` и `1,1,1`),
      причём каждое соединение живёт ровно текущий backoff **другой** лестницы (1/2/4/8/16 с).
      Детерминированное репро: `adb shell am start -n ru.sipaha.sawe.app/.MainActivity` на
      подключённом приложении убивал живое 122-секундное соединение.
      **Исправлено двумя слоями.** (1) `android:launchMode="singleTask"` на `.MainActivity` —
      `singleTop` **не подходит**, он схлопывает повторный запуск только когда Activity уже наверху
      задачи; приложение однокативитное, терять под собой нечего. `onNewIntent` **не понадобился** и
      это проверено: ни одна строка `app/src/main/kotlin` не читает Intent Activity, intent-filter
      единственный (`MAIN`/`LAUNCHER`, без `<data>`), а QR-сканер и оба пикера ходят через
      `rememberLauncherForActivityResult` — их результат приходит по пути `onActivityResult`, а не
      `onNewIntent`; пустой оверрайд был бы мёртвым кодом. (2) Файловый `private object
      ConnectionGuard` в `ConnectionManager.kt`: слабая ссылка на текущего владельца соединения,
      регистрация в пути привязки (`switchToServerLocked`, **до** присваивания `client`, чтобы не
      существовало мгновения с двумя живыми клиентами), политика «побеждает последняя привязка» —
      прежний владелец сносится через существующий `tearDownConnection()` → `RemoteClient.close()`,
      то есть по штатному контракту передачи (запаркованные записи очереди остаются на диске
      следующему клиенту и **не** возвращаются в композер; отбиваются только ушедшие в транспорт
      кадры). Второго пути сноса не заводили. Срабатывание пишется `Log.e` с тегом `ConnectionGuard`
      и обоими идентификаторами (`CM#1` / `CM#2`, монотонный счётчик, не хеш) — чтобы повтор в поле
      искался грепом, а не ещё одной инструментированной сборкой. Обычный цикл одного менеджера не
      тронут: `unbind` стоит **после** идемпотентного быстрого выхода `tearDownConnection`.
      В `:core` добавлено единственное — публичное чтение `RemoteClient.isClosed` поверх уже
      существовавшего `closing`, чтобы тест утверждал факт передачи, а не строку в логе
      (`connectionState` читается `Disconnected` и у закрытого клиента, и у ни разу не звонившего).
      **Почему аудит это пропустил:** каждый его тест конструирует ровно один клиент, все находки
      формулировались внутри одного экземпляра, а то, что менеджеров бывает больше одного, следует
      из **манифеста** — файла, который в скоуп «сетевой путь» не входил.
      Тесты: `DuplicateConnectionGuardTest` (6, Robolectric, два настоящих `ConnectionManager` на
      мёртвом loopback-порту) и `ClientHandoffTest` (3, `FakeRemoteTransport`). Проверено, что без
      стража падают оба ключевых случая (без него: «two clients per process» и
      `[Connecting, Reconnecting(attempt=2, nextRetryMs=2000, …)]` — ровно вторая лестница из лога), а
      без атрибута в манифесте падает скан манифеста. `:core` 464, `:app` 459, `:app:assembleRelease`
      зелёные. **На устройстве не проверялось** — телефон разработчика недоступен.
